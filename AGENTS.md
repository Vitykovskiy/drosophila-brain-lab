# Правила работы агентов

- Принципы применяются всегда, кроме случаев, когда пользователь прямо просит об обратном.

## Приоритеты принципов
- КРИТИЧНО: При выборе между упрощением и необоснованным усложнением всегда выбирайте простое решение. Каждый агент и подагент обязан сверяться с этим правилом и отклонять необоснованное усложнение.
- При конфликте правил применяйте приоритеты в таком порядке: корректность, безопасность, проверяемость, сопровождаемость, простота, скорость и лаконичность.
- Краткость не должна скрывать существенный риск, ошибку в предпосылках, архитектурное ограничение или причину выбранного решения.
- Простота не должна нарушать инварианты, обратную совместимость, тестируемость, границы ответственности и требования эксплуатации.

## Обязательные пакты
- КРИТИЧНО: Соблюдай `codex-communication-pact` во всех ответах пользователю; отделяй факты, выводы и неизвестность, сохраняй условия, числа и единицы измерения.
- КРИТИЧНО: Соблюдай `codex-orchestration-pact` при комплексных задачах; локальную правку выполняй напрямую, при делегировании передавай исходный запрос без пересказа и сохраняй границы ролей.
- КРИТИЧНО: Соблюдай `codex-documentation-pact` при создании, правке и ревью документации; проверяй источники и ссылки, отделяй текущее состояние от требований и решений.
- КРИТИЧНО: Соблюдай `codex-development-pact` при создании, правке и ревью кода; если задача затрагивает UI, соблюдай `codex-ui-analysis-pact` при анализе и документировании его поведения.
- Читай применимый `SKILL.md` до действий; нарушение пакта считается ошибкой выполнения задачи, при замечании пользователя исправляй результат по соответствующему порядку исправления.

## Навыки для документации
- При работе с документацией используй `documentation` для выбора применимых этапов процесса и `documentation-templates` для структуры; адаптируй шаблоны к задаче и существующим соглашениям.
- Используй `documentation-generation-doc-generate` при создании документации из кода, конфигурации и комментариев; утверждения выводи из прочитанных первичных источников.
- Используй `docs-architect` при проектировании структуры документации и подготовке подробного технического описания архитектуры, компонентов и потоков данных.
- Используй `documentation-and-adrs` для фиксации значимых решений, их причин, альтернатив и последствий; сохраняй существующие соглашения ADR и историю заменённых решений.
- После создания или изменения документации обязательно применяй `docs-guard`: сверяй утверждения, символы, примеры и ссылки с источниками; явно отмечай недоступные проверки.
- Выбирай навыки по указанным условиям и читай их `SKILL.md` до применения; создание сайта документации, генераторов, CI и проверочной автоматизации требует отдельного прямого поручения.

## Контекст и ключевые соглашения
- Область работы — оцифрованный мозг дрозофилы; текущая реализация — вычислительная модель на основе коннектома, а не полное воспроизведение биологического мозга.
- Точка входа: [Readme.md](Drosophila_brain_model/Readme.md); модель: [model.py](Drosophila_brain_model/model.py); обработка результатов: [utils.py](Drosophila_brain_model/utils.py).
- Пример работы: [example.ipynb](Drosophila_brain_model/example.ipynb); расчёты для рисунков исходной работы: [figures.ipynb](Drosophila_brain_model/figures.ipynb). Читай только релевантные файлы и ячейки.
- Сохраняй различие между данными коннектома, допущениями модели, результатами симуляции и биологическими выводами; выводы ограничивай имеющимися свидетельствами.
- Не смешивай версии FlyWire 630 и 783: `path_comp` и `path_con` должны относиться к одной версии; сохраняй соответствие FlyWire ID и индексов Brian 2.
- Сохраняй размерности Brian 2, смысл параметров, направление и знак синаптических связей, контракты входных данных и результатов, если задача прямо не требует их изменения.
- Для новых экспериментов фиксируй версию и источники данных, параметры, длительность, число повторов, окружение и условия случайности; отсутствие фиксированного seed обозначай явно.
- Исходные данные и `results/example/` сохраняй; новые результаты записывай отдельно, не включай `force_overwrite=True` без прямого разрешения на перезапись.
- После нетривиальной правки актуализируй затронутую документацию или пояснения ноутбука; подробное правило держи в одном основном источнике.

## Менеджер окружения
- Используй Conda и [environment.yml](Drosophila_brain_model/environment.yml): Python 3.10, Brian 2.5.1, NumPy 1.24. Команды ниже выполняются из `Drosophila_brain_model/`.
- [environment_full.yml](Drosophila_brain_model/environment_full.yml) содержит версии исходной работы и платформенные сборки Windows; не считай его универсальным окружением для текущей машины.
```bash
conda env create -f environment.yml
conda activate brian2
jupyter notebook example.ipynb
```

## Проверки отдельных файлов
- В текущем дереве нет настроенных команд линтера, форматтера, тестов или CI; не выдумывай команды и не выдавай чтение исходников за запуск модели.
- Выбирай релевантную существующую проверку для изменённого файла или ячейки; не запускай весь `figures.ipynb` как обязательную проверку любой правки.
- Тесты не меняй и не запускай, пока пользователь прямо не включит их в текущую задачу; новые тесты, валидаторы и проверочные скрипты создавай только по отдельному прямому поручению.
- Если тесты поручены, размещай их рядом с тестируемым файлом и пиши имена тестов на русском в допустимой для инструмента форме.
- Доступность UI не анализируй, не проверяй, не меняй и не выноси в замечания, пока пользователь прямо не включит её в текущую задачу.
- Перед завершением нетривиальной задачи по возможности выполняй релевантные разрешённые проверки; в итоговом ответе отделяй выполненные проверки от незапущенных и неприменимых.

## Границы автономности и Git
- Без отдельного подтверждения выполняй порученные изменения Python-кода, ноутбуков и документации по существующим паттернам, разрешённые проверки и рабочие артефакты в `.codex/<task-name>/`.
- Прямое поручение или явное подтверждение требуется для `git commit`, `git push`, force-push, tag и создания PR; крупных обновлений зависимостей; инфраструктурных правок, меняющих поведение окружения; крупных архитектурных изменений; удаления используемого публичного API или функциональности.
- Изменение научных допущений, уравнений, исходных данных и перезапись сохранённых результатов должны быть прямо включены в задачу или явно подтверждены пользователем.
- Commit не считается новой задачей разработки; проверки, уже подтверждённые для того же diff, повторно не запускаются.
